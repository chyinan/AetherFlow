# 保存响应丢失后的版本恢复

## 场景

已保存的工作流在本地与服务器版本都是 N。用户编辑得到内容 A 并点击保存，后端实际完成更新、把 A 保存为 N+1，但成功响应超时或连接中断，前端没有收到。前端仍保留 `backendVersion=N`，用户继续编辑得到 B 并再次保存，后续请求一直携带旧版本 N，持续版本冲突。

A 没有丢失，B 也不是立即丢失；缺陷是一次网络故障之后缺少保留后续编辑的恢复保存路径。重新加载可以拿回 A 和新版本，但会替换当前 B 并清空撤销重做历史。

## 恢复契约

- 后端的乐观锁是正确保护，不能删除版本校验或强制覆盖
- 保存前固定一份不可变提交快照：工作流归属、期望版本 N 与实际发出的业务内容
- 只有“请求可能已经落库、但响应没有回来”的失败才触发核对。服务端明确拒绝（校验失败、版本冲突等 4xx）时结果是确定的，不发起核对请求
- 核对只读远端定义，不使用 `loadWorkflow` 覆盖当前画布
- 只有远端版本正好是 N+1 且业务内容与提交快照完整一致，才算确认已提交。名称、节点数或部分字段相同不算
- 业务内容比较覆盖本次更新可修改的全部字段（名称、描述、所属项目、节点 ID／类型／标题／位置／配置），排除版本与服务端生成的字段，并正确处理服务端规范化
- 确认已提交且没有较新编辑时才清除未保存标记；存在较新编辑时保留 B、选中状态与撤销重做历史，只更新保存基线与版本，B 仍为未保存
- 远端内容不符、版本不符或核对请求失败时保留本地草稿并给出明确下一步，不自动覆盖远端，也不静默重载
- 远端在核对之后再次更新，后续保存仍由乐观锁阻止覆盖
- 核对结果绑定原工作流与本次保存；切页、重载、新保存或较新的核对都不得让旧结果写回
- 首次创建沿用既有幂等键恢复：重试携带同一个幂等键会拿回原记录
- 结果不确定的提交快照跨保存保留：核对读回全部失败后，下一次保存先重新核对远端再提交新编辑，确认已落库就更新保存基线并用新版本保存；不能只把快照留在单次调用的局部变量里
- 真正远端冲突时不提交新编辑、不覆盖远端，本地草稿保留并提示下一步
- 保存后离开、复制前保存、运行前保存复用同一保存路径，发现真正冲突时不得继续错误导航或运行

## 恢复状态

`uncertain`（响应未返回）、`reconciling`（正在核对）、`committed`（确认已提交）、`committedWithNewerEdits`（确认已提交但存在较新本地编辑）、`notSubmitted`（确定未提交）、`conflict`（真正远端冲突）、`retryable`（核对失败可重试）。

## 验证范围

前端回归使用真实 store、真实 API 映射与受控延迟 Promise，后端替身确实记录“已提交并版本递增、但响应失败”。覆盖：已提交且无后续编辑、已提交且用户编辑到 B、核对等待期间继续编辑 C、请求实际未落库、他人修改远端、远端版本超出预期、读回失败、服务端明确拒绝不触发核对、切换工作流后旧核对不写回，以及纯函数层的键顺序、节点顺序与业务字段局部不同。

受控替身与 jsdom 用例不等于真实网络、真实后端或浏览器验收。
