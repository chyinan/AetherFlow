# AI 节点任务类型与执行器别名

## 场景

工作流目录与运行事件使用 `WHISPER` 表示语音转写节点，ai-service 的执行器只登记 `ASR`。默认异步执行启用时，工作流服务把 `WHISPER` 任务派发给 task-service，队列消息与监听器都原样保留该类型。

## 契约

- 异步链路与同步链路共用同一处执行器解析边界：`DefaultAiNodeExecutorRegistry`。别名在这里解析，两条链路同时生效
- `WHISPER` 解析到 `ASR` 执行器；未知类型仍按原始类型明确报错（`unsupported ai node type: <type>`），不被错误接纳
- 持久化任务的原始类型不变：任务记录与队列消息仍是 `WHISPER`，任务标识、幂等键与消息载荷语义不变
- 能力展示不变：注册表对外暴露的可执行类型集合仍是真实执行器类型（`ASR`），能力快照按既有口径把 `ASR` 呈现为 `WHISPER`
- 结果契约不变：执行结果沿用执行器自身的节点类型，与同步入口一致
- 大小写与首尾空格归一化沿用既有行为（`trim` + `uppercase`），别名同样适用

## 为什么不在同步控制器上单独处理

同步入口（`AiWorkflowNodeController`）此前已把 `WHISPER` 转换为 `ASR` 后再查注册表，异步链路没有这一步，因此在真正调用 Python 之前就失败。只在同步入口修别名不能覆盖异步路径，重试同一类型也不会解决根因。

## 验证范围

Java 回归覆盖：worker 用真实注册表与真实 ASR 执行器接收真实 dispatcher 产出的任务消息形状（`nodeType=WHISPER`）后成功执行；未知类型仍被拒绝；别名与既有大小写、首尾空格归一化并存；注册表暴露的可执行类型集合不变。dispatcher 侧回归确认派发消息的类型、任务标识与幂等键未变。

测试中的 Python ASR 由受控替身返回，属于受控集成测试，不代表真实语音服务或真实模型验收。
