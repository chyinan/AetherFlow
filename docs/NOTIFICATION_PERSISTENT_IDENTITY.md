# 通知的持久化身份

## 场景

服务端落库后推送的通知携带 `eventId`，该值就是通知记录 ID。前端丢弃它，改用
"时间 + 随机数"生成实时通知的界面 ID；历史列表则用"记录 ID"生成另一个 ID。同一��通知
经实时推送与历史读取两条路径到达时是两条不同的记录，界面重复展示，未读数可能由 1 变 2。

## 契约

- 实时推送使用服务端持久化身份（`eventId`），与历史列表里的同一条通知是同一个 ID
- 合并按持久化身份进行，不按文案去重：同内容但不同记录的通知各自保留
- 没有持久化身份的临时本地提示（连接状态提示等）继续按本地提示保留，不被后端快照挤掉
- 重复回放同一条实时消息只保留一条
- 历史读取期间新到的通知不在该次快照里，合并时必须保留，不能按"后端没有"丢弃
- 后端快照仍然对已有记录具有权威性：后端已不存在的旧记录不会复活
- 已读状态以服务端为准，关闭重开保持一致

## 验证范围

前端 store 测试覆盖：实时与历史先后两种顺序、重复回放、同内容不同记录、无持久化身份的
本地提示、历史请求期间到达的新通知；既有通知恢复用例保持通过。
