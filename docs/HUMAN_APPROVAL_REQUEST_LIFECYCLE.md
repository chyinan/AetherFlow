# 人工审批请求的目标与生命周期

## 用户可见的问题

运行历史页中的审批框可能被同一运行的下一审批节点、或已经缓存的另一运行复用。
原实现把迟到回执应用到“此刻第一个待审批节点”，没有绑定原提交目标：

- 对节点 A 提交后，刷新恢复先进入节点 B，A 的回执会把 B 在前端错误标为已批准/成功，隐藏 B 的审批入口；后续等待快照也无法覆盖这个错误节点终态
- 切到已缓存的另一运行时，旧回执还会改写新运行的前端运行时 ID，导致新运行实时事件被归属检查忽略
- 下一审批继承前一审批的备注、提交等待或错误；已结束/取消运行的历史 pending 节点也可能在刷新时重新打开审批框

以上是前端状态与操作上下文错误，不代表服务端执行了未经提交的审批。回归明确检查没有向下一节点自动发出审批请求。

## 当前行为

1. 每次审批提交固定实例 ID、节点 ID 和请求代际，成功、失败、等待清理均只属于该次目标
2. 切换实例或节点时清空旧意见、错误和提交等待；同一目标只更新展示信息时保留用户输入和正在进行的请求
3. 关闭、Esc、点击遮罩或卸载使旧回执失效；关闭不承诺撤销已经到达后端的审批，重新打开后仍以恢复结果为准
4. 完成事件携带原始目标；页面再次核对当前有效审批，只更新相同实例的相同节点
5. 只有暂停且仍待审批的节点可以打开审批；后端已确认 SUCCESS、FAILED 或 CANCELLED 时隐藏审批操作。未确认的局部推断终态不替代后端终态
6. 当前请求失败保留意见，可由用户重试；重复点击仍只发送一次请求

## 回归与验证边界

正式回归使用真实 RunsPage、HumanApprovalDialog、Pinia、Vue Router、HTTP API 模块和运行事件 mapper。HTTP 与实时传输边界使用受控替身，覆盖批量刷新推进下一节点、并行新旧回执、已缓存跨运行导航、关闭后重开、三种终态、失败重试及重复点击。

独立复核另外覆盖 A→B→A 重入、同目标信息更新、卸载和迟到失败。验证不是实际浏览器像素、生产后端、审批服务或 Provider 验收；没有改变审批 API、服务端权限、审批决策语义或节点终态保护。
