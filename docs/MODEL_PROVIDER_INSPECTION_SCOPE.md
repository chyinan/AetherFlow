# 服务商检查流程的对象归属与状态呈现

## 范围与问题

本轮基于维护分支 `ed347e543cb918ab22d0c20f3c86cc426b01808f`，只处理 `/models` 管理页的“看整体概况 → 选择服务商 → 检查所选服务状态与模型”流程。它延续 [前端逐页任务层级检查](FRONTEND_PAGE_HIERARCHY_REVIEW.md) 中记录的服务管理候选，不重复已合并的运行页、节点目录或共享浮层修改。

原页面前两张概况卡是平台在线提供商与就绪模型计数，后两张却读取所选提供商的延迟和配额。其中延迟仍标成“主路由延迟”。普通选择备用服务不会执行路由切换，却会让这张卡显示备用服务的延迟，容易误导故障判断。

固定夹具的反例不依赖新增测试标识：主服务甲仍为活动路由、探测延迟 145ms；点击原有“备用服务乙”按钮只执行内存选择，旧主路由卡却显示“主路由延迟760ms后端运行探测”。基线断言在这条文本上失败。这是数据对象归属缺陷；紧凑布局本身属于设计改进，尚无真实用户研究或视觉验收证明其效果。

## 修复后的呈现契约

- “整体服务概况”是具名的紧凑区域，仅包含在线提供商与就绪模型两项全局计数，以及原有注册数量、目录条目说明，普通选择不会改变其对象范围
- 所选服务详情以真实标题和服务名称命名，延迟、配额与模型位于该范围内；延迟仍保留“后端运行探测”来源，不冒充业务请求耗时或主路由指标
- 本地服务继续显示配额不适用；没有正延迟样本时显示未知占位，不虚构零耗时
- 列表保留原生按钮，补充 `aria-pressed` 与受控详情关联；选中样式和程序化状态跟随实际详情对象，包括既有 getter 的首项回退
- 普通选择、重复选择和往返选择不新增焦点跳转。服务快照独立以同一服务名命名，完整端点、健康、熔断、能力、检查时间及原因仍然可见
- 全局运行日志保留原有作用域，没有被包进所选服务名称下；列表诊断与路由策略也没有折叠或删除

没有修改 store、API、管理动作、权限与能力门禁、身份监听、路由、用户设置或持久化。

## 加载、失败与恢复

| 状态 | 用户看到的内容与下一步 |
| --- | --- |
| 首次加载，无快照 | 保留加载提示，整体数尚未确认，不呈现成功零计数 |
| 首次读取失败 | 保留错误、未确认说明和显式重试，不显示成功空快照提示 |
| 成功返回空 | 显示已确认的零服务/零模型与既有空提示、配置入口，没有残留服务指标 |
| 已选择服务 | 整体计数稳定；详情名称、延迟、配额、模型对应所选对象 |
| 保留旧快照刷新 | 保留旧选择与详情，同时显示加载提示，不冒充刷新已完成 |
| 刷新失败，有旧快照 | 保留旧详情与“上次成功数据”警示，可显式重试读取，不重新派发管理写操作 |

该流程没有新增表单、模态或待提交草稿；可直接改选另一服务或离开页面。离开/返回继续沿用既有生命周期，没有新增恢复或存储承诺。真实网络竞态、服务故障恢复与管理写操作不属于本轮验证。

## 验证与限制

仅执行 `frontend/src/pages/models/ModelsPage.presentation.test.ts` 中经逐项审阅的 16 项受控 DOM 用例。完整 mock `authStore`、`modelStore`、普通服务目录及 API client，固定单一管理界面；禁止真实 fetch、XMLHttpRequest、WebSocket、EventSource 和管理写操作。选择仅更新内存，刷新只是替身；不执行真实身份切换、服务路由切换、恢复或配置操作。

覆盖：精确误报反例、整体/所选指标边界、详情名称与数据对应、原生按钮选中语义、失效选择标识回退、重复选择/程序化焦点、本地额度/未知延迟、首次加载/失败/空、旧快照刷新/失败、长名称/端点以及中英日文案。

基线 16 项均失败，其中精确误报反例明确收到错误的“主路由延迟760ms”文本；其他结构用例主要因新区域尚不存在而失败，不能将它们全部称为独立业务缺陷复现。实现后的同一文件初次 16 项全部通过；独立复核随后要求保留探测来源，并补强实际翻译断言，未降低原有期望。

最终 16 项由独立审查重新执行，全部通过（2026-10-17 17:58 UTC）。`vue-tsc` 的应用与构建配置类型检查均通过，Vite 生产构建通过。构建仍提示既有的大于 500kB 分块，最大工作流页约 565.08kB；这不是性能验收。独立源码复核确认生产改动只涉及页面呈现与局部三语文案，没有剩余源码/受控 DOM 阻断。
